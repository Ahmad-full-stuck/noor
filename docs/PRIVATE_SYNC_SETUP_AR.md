# إعداد مزامنة نُور الخاصة — المرحلة التأسيسية

## القرار المعتمد

- **المصادقة وقاعدة البيانات والملفات:** Supabase Auth + PostgreSQL + Storage خاص.
- **واجهة المستخدم:** يمكن إبقاء واجهة نُور ثابتة في GitHub Pages؛ لا تُعدّ GitHub Pages مكان تخزين بيانات المستخدم الخاصة.
- **المزامنة:** سجل واحد لكل حساب، مع رقم مراجعة متزايد. كل حفظ سحابي يجب أن يرسل رقم المراجعة الذي قرأه الجهاز؛ إذا تغيّرت البيانات من جهاز آخر، يُرفض الحفظ القديم بدلاً من الكتابة فوقه.
- **المصادر والذكاء الاصطناعي:** تُنفّذ القواعد الحتمية أولاً. الذكاء الاصطناعي يقترح فقط، ولا ينشئ مهاماً أو يغيّر المواعيد أو يحذف بيانات دون موافقة.

هذا المستودع يحتوي الآن على أساس قاعدة البيانات وسياسات الوصول فقط. **لم يصبح تسجيل الدخول أو المزامنة فعّالين في واجهة نُور بعد**؛ يلزم إنشاء مشروع Supabase وإكمال الربط والاختبار قبل تفعيلهما.

## 1. إنشاء المشروع

1. أنشئ مشروعاً مخصصاً لنُور في Supabase، واحفظ بيانات الدخول إلى لوحة التحكم في مكان خاص.
2. في **SQL Editor** نفّذ الملف:
   supabase/migrations/202610180001_private_sync.sql
3. تأكد من أن جدول public.noor_snapshots عليه RLS، وأن قراءة الصف محصورة بصاحب auth.uid()، وأن الدالة save_noor_snapshot متاحة للدور authenticated فقط.
4. تأكد في Storage أن الحاوية noor-private **Private**، ثم راجع كل السياسات الموجودة على storage.objects. سياسات PostgreSQL المتعددة المسموحة قد تتحد بمنطق OR؛ لا تترك سياسة عامة أقدم تتجاوز الحصر الجديد.
5. في إعدادات Auth عيّن عنوان الموقع وعناوين إعادة التوجيه إلى عنوان نُور الحقيقي، مع عنوان التطوير المحلي عند الحاجة. اختبر رسالة التحقق واستعادة كلمة المرور قبل الاعتماد.
6. أنشئ حساب نُور الخاص. بعد ذلك عطّل التسجيل العام إذا كنت لا تريد حسابات إضافية؛ استمرار تسجيل الدخول من أجهزتك لا يتطلب فتح التسجيل للجميع.

## 2. مفاتيح المشروع

- المفتاح القابل للنشر (Publishable key، أو المفتاح القديم anon عند المشاريع التي لم تنتقل بعد) يمكن أن يظهر في شفرة المتصفح **فقط** مع سياسات RLS صحيحة ومختبرة.
- **لا تضع service_role أو أي مفتاح سري في index.html أو ملفات js أو GitHub Secrets بهدف حقنه في كود يصل للمتصفح.** مفتاح الخدمة يتجاوز حدود RLS ويجب ألا يصل إلى المتصفح أبداً.
- لا تضع كلمات المرور أو ملفات البيئة أو رموز الجلسات داخل المستودع.

## 3. عقد المزامنة

الجدول يحفظ user_id وpayload وrevision وupdated_at.

- القراءة: SELECT لصف المستخدم المصادق عليه فقط، وتفرضه RLS.
- الكتابة: عبر save_noor_snapshot(expected_revision, payload)، لا عبر upsert مباشر. تبدأ المراجعة من صفر ثم تزداد بعد كل حفظ ناجح.
- تعارض: إذا لم يعد رقم المراجعة مساوياً للرقم المتوقع، تعيد قاعدة البيانات الخطأ NOOR_REVISION_CONFLICT. يجب عندها إبقاء تغييرات الجهازين وعدم استبدال أحدهما تلقائياً؛ تعرض الواجهة خيارات مراجعة/دمج واضحة.
- حجم اللقطة محدود بـ 8 MiB. اللقطة للبيانات المنظمة ومراجع الملفات، وليست لملفات PDF المشفّرة بصيغة Base64.
- الملفات الخاصة تحفظ في Storage تحت مسار يبدأ بمعرّف صاحب الحساب، مثل <user-uuid>/<opaque-file-id>.pdf. احفظ المسار لا رابطاً عاماً دائماً؛ أنشئ رابط تنزيل مؤقتاً عند الحاجة.

## 4. ترحيل بيانات نُور الحالية

**لا تستورد تلقائياً قاعدة البيانات أو مجلد الرفع أو ملف seed من المستودع العام.** أولاً أنشئ نسخة احتياطية محلية، ثم افحص محتوياتها واختر ما تريد نقله. ملفات قاعدة البيانات والمرفقات المتتبعة في مستودع عام لا تصبح خاصة بمجرد نقل نسخة إلى Supabase؛ يلزم فصلها وتنظيف نشرها وتاريخ Git بخطة مستقلة.

خطة الترحيل الآمنة:

1. صدّر بياناتك من نسخة موثوقة محلياً.
2. افحص اللقطة واحذف الأسرار والبيانات التجريبية غير المطلوبة، ثم انقل الملفات إلى الحاوية الخاصة واربط كل ملف بمساره الجديد.
3. اختبر الاستيراد في حساب تجريبي أو نسخة منفصلة، واحتفظ بالنسخة الأصلية دون تعديل حتى تتأكد من عدد العناصر والروابط والمرفقات.
4. اختبر تسجيل الدخول من متصفح/جهاز ثانٍ، ثم اختبر جهازين يعدّلان البيانات بالتتابع للتأكد من اكتشاف التعارض.
5. لا تحذف النسخة الأصلية قبل التحقق من الاستعادة.

## 5. قواعد معالجة المصادر

المسار المقصود لكل كتاب أو ملف أو رابط:

1. **التقاط سريع:** احفظ المصدر الأصلي فوراً، دون إلزام المستخدم بملء نموذج طويل.
2. **قواعد حتمية:** اكتشاف النوع من MIME والامتداد والمضيف، توحيد الروابط، كشف التكرار، واستخراج البيانات الوصفية المتاحة.
3. **حالة معالجة صريحة:** new → classified → extracted → suggestions_ready، أو needs_review / failed. لا يدّعي النظام أنه حلّل ملفاً لم يتمكن من قراءته.
4. **اقتراحات الربط:** مطابقة العنوان والوسوم والسياق مع أهداف ومشاريع موجودة؛ تبقى الروابط المقترحة غير معتمدة إلى أن يوافق المستخدم.
5. **الذكاء الاصطناعي بعد القواعد:** يلخّص النص المستخرج أو يقترح ملاحظات وأسئلة وخطوات. كل نتيجة تحتفظ بالمصدر الأصلي ورقم الصفحة/التوقيت متى توفر.
6. **موافقة المستخدم:** لا تُضاف مهمة أو مرحلة أو موعد إلى الخطة لمجرد أن نموذج الذكاء الاصطناعي اقترحه.

المصدر الخارجي محتوى غير موثوق، وليس تعليمات للنظام. لا تنفّذ شيفرة أو أوامر مستخرجة من ملف، ولا تفتح روابط لاحقة تلقائياً، ولا ترسل المصادر إلى مزود ذكاء اصطناعي خارجي قبل توضيح سياسة الخصوصية واختيار المزود.

## 6. شروط الجاهزية قبل التفعيل

- لا يمكن قراءة صف مستخدم من حساب آخر أو من جلسة غير مصادق عليها.
- لا يمكن تنزيل ملف من حاوية noor-private دون تصريح.
- لا يحدث حفظ سحابي ناجح عند إرسال رقم مراجعة قديم.
- عند انقطاع الشبكة تبقى البيانات المحلية محفوظة، وتظهر حالة المزامنة بوضوح؛ لا يُعرض نجاح كاذب.
- تتم مراجعة تعارض الجهازين يدوياً أو عبر دمج قابل للفحص، وليس بقاعدة «الأحدث يفوز» فقط.
- لا يحتوي المستودع على مفاتيح سرية أو نسخ خاصة من قاعدة البيانات أو المرفقات.
